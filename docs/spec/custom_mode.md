# custom_mode

## 目的
通常版では扱わない個人差（補給・心拍管理・レース運び）を反映し、個別最適化する。

## MVP設定項目（7つ）
1. `fuelMode`（`off` / `time`）
2. `firstFuelAfterMin`（初回補給タイミング）
3. `fuelIntervalMin`（補給間隔）
4. `fuelAlertLeadMin`（補給予告の早さ）
5. `phaseAggressiveness`（走り方強度 0..20）
6. `hrCapBiasBpm`（心拍上限バイアス -8..+8）
7. `driftSensitivity`（予約値 0..7）

## 補給設定MVP方針
- `fuelMode=off`: 補給通知なし
- `fuelMode=time`: 時間ベース補給通知
  - `firstFuelAfterMin` で初回通知
  - 以降 `fuelIntervalMin` ごとに通知
  - 予定時刻の `fuelAlertLeadMin` 分前から予告

※ 距離ベース補給（`fuelMode=distance`）は将来拡張。MVP対象外。

## 設計方針
- ユーザーに見せる項目は7つに限定
- 内部の専門閾値は公開せず、抽象設定から展開する
- 通常版はシンプル維持、カスタムモードのみ個別最適化
- `driftSensitivity` はカスタムコード互換維持のため構造上は残すが、現行表示・判定では使用しない

## カスタムコード方針
- 7項目の設定値を短いカスタムコードへ符号化して受け渡す
- コードに含める要素:
  - バージョン情報
  - 設定本体
  - 誤入力検知用チェック値
- 目的は機密化ではなく、運用性/入力性/拡張性

## 初期実装で非公開の内部パラメタ（例）
- フェーズ境界の細かな進行率
- 心拍オーバー判定秒数/解除秒数/解除オフセット
- ペース押し上げ判定秒差
- push時の心拍余裕幅
- cardiac cost 関連比率
- 通知固定表示秒数
- 誤操作防止デバウンス秒数

## 将来拡張候補: フェーズ別の直接指定

### 位置づけ
- MVPの7項目は維持する
- 直接指定は、FIT分析とヒアリングを前提にしたカスタム版の将来拡張として扱う
- 通常版には含めない

### ねらい
- 利用者が「なぜこの指示になるのか」を自分のレースプランとして理解しやすくする
- 単一の目標タイム由来ペースだけでは表しにくい、前半抑制・中盤巡航・終盤解放を明示できるようにする
- カスタム版の納品物である分析レポートと、実機での挙動を一致させる

### 採用方針
- 直接指定する対象は「平均心拍目標」ではなく、各フェーズの `目標ペース帯` と `心拍上限` を基本とする
- 心拍は環境要因でぶれやすいため、追い込みの目安ではなく安全側の上限として扱う
- 平均心拍はレポートには載せてよいが、実機制御の主パラメタにはしない

### フェーズ定義
- フェーズ数は既存の `S1..S5` をそのまま使う
- 境界は通常ロジックと同じ進行率ベースとする
  - `S1`: `< 24%`
  - `S2`: `24%〜59%`
  - `S3`: `59%〜83%`
  - `S4`: `83%〜95%`
  - `S5`: `95%〜Finish`

### 直接指定データの最小形
- 各フェーズで保持する値は3つ
  - `paceMinSecPerKm`
  - `paceMaxSecPerKm`
  - `hrCapBpm`
- 補助用途として、レポートや納品メモには以下を持ってよい
  - フェーズ名
  - 意図ラベル（例: 抑える / 整える / 固定する / 守る / 解放する）
  - 作成根拠メモ

### 実機での優先順位
- ペース判定は、単一の `targetPaceSecPerKm` ではなく、現在フェーズの `目標ペース帯` に対して評価する
- 心拍判定は、Garmin心拍ゾーン由来の上限ではなく、現在フェーズの `hrCapBpm` を優先する
- ただし安全側のため、Garmin由来上限より厳しい値を設定した場合はそのまま採用し、緩い値を設定した場合は上限緩和幅を別途制限する

### ACTIONとの整合
- `ちょい上げ`: 現在ペースが `paceMaxSecPerKm` より遅く、心拍が `hrCapBpm` 未満のときに候補にする
- `そのまま`: 現在ペースが `paceMinSecPerKm..paceMaxSecPerKm` の範囲で、心拍超過がないときの基本状態とする
- `ちょい落とし`: 現在ペースが `paceMinSecPerKm` より速い、または `hrCapBpm` を超過した場合に優先して出す
- ペース帯と心拍上限が矛盾した場合は、失速防止を優先して心拍側を優先する

### UI方針
- 走行中の画面文言は増やさず、既存の `ちょい上げ / ちょい落とし / そのまま` を維持する
- フェーズ別の数値を常時表示するのではなく、事前のレポートまたは設定確認で見せる
- 実機UIは「理解した計画を実行する場」であり、「計画を読む場」にはしない

### 運用方針
- 初期導入は、アプリ内の自由設定ではなく、分析レポートから生成するカスタムコード経由を前提とする
- まずは「フェーズ別の目標表を納品するが、アプリ内制御は従来どおり」の運用でもよい
- 実需要が確認できた段階で、カスタムコードに `phasePlan` 相当を載せる

### 注意点
- フェーズ別の直接指定を入れると、設定自由度は上がる一方で、作成ミス時の破壊力も大きい
- 気温・高低差・当日の体調でズレるため、固定ペース一点指定より「許容帯」で持つ
- 実装時は、既存の7項目コード体系との共存方法と後方互換を先に決める
