# Threads Post Writer

Threads 投稿を、実際の既存投稿と市民ランナーの実感に合わせて作る。

## Quick Flow

1. `references/racenavi-threads-context.md` を読む。
2. `https://www.threads.com/@eba3.run` の既存投稿を毎回確認する。
3. 反応傾向を短く整理する。
4. その分析を踏まえて投稿案を 10 件作る。

## Live Check

- Threads の反応は変動する前提で、過去の記憶ではなく毎回ブラウズして確認する。
- 確認先はまず公式プロフィール `https://www.threads.com/@eba3.run` を優先する。
- 既存投稿の確認は毎回必須。確認前に文案作成を始めない。
- 直近で見える投稿本文、投稿日、いいね数、返信の有無を優先して確認する。
- 可能なら次を整理する:
  - どの投稿にいいねが多いか
  - どの投稿に返信がついているか
  - どの投稿がインプレッションを取りやすそうか
  - 投稿の長さ、書き出し、話題、口調、締め方の傾向
  - RaceNavi系、関門ガイド系、練習・レース体験系、開発裏話系のどれが反応を取りやすいか
  - 反応が弱そうな投稿に共通する点
  - 説明っぽくなりすぎていないか
  - ランナーが「それ分かる」と思える具体的な場面があるか
- インプレッション数を外部から確認できない場合は、そのことを明記し、いいね数・返信数・投稿内容から推定する。
- ページが見られない、投稿本文が十分に拾えない、反応数が読めない場合は、その不足を隠さない。
- Threads ページを確認できない場合は、ユーザーに直近投稿と実績の貼り付けを依頼する。そのうえで、`references/racenavi-threads-context.md` に基づく仮説案は先に出してよい。
- 日付は可能なら絶対日付で扱う。

## Writing Rules

- 1 回の出力で必ず 10 件作る。
- RaceNavi と関門ガイドを両方混ぜる。ただし 5:5 に固定しない。
- 投稿は説明から入らず、レース中や開発中の具体的な場面から入る。
- 機能紹介より、困りごと、焦り、判断ミス、あるあるを先に出す。
- 最後だけ質問で締めない。無理な CTA を付けない。
- 返信を狙う場合も、本文の中に自然な余白やツッコミどころを残す。
- 少し軽く、少し自虐は可。ただしふざけすぎない。
- 宣伝臭を強くしない。`便利です` `ぜひ使ってください` `おすすめです` は避ける。
- 実走して分かったこと、後半で余裕がなくなった自分、Garmin の見づらさを重視する。
- ハッシュタグは原則なし。必要でも最小限。
- リンクや導線は原則なし。入れるとしても 10 件中 0〜2 件までに抑え、売り込みではなく自然に触れる程度にする。
- 画像が合う投稿だけ、コードブロックの外に 1 行で画像案を添える。

## Output Format

最終出力は毎回この順でそろえる。

1. `【既存投稿の分析】`
2. 以下 3 行
   - `- 反応が良さそうな傾向：`
   - `- 反応が弱そうな傾向：`
   - `- 今回狙う方向性：`
3. `【投稿案1：RaceNavi】` のような見出しを付けて、10 件分を順に出す
4. 各本文は必ず個別のコードブロックに入れる
5. 最後に `【狙い】` と 1〜10 の 1 行要約を付ける

## Repo Context

- まず `references/racenavi-threads-context.md` を読む。
- 追加確認が必要なときだけ以下を見る:
  - `PRODUCT.md`
  - `TASKS.md`
  - `tasks/09-3_sns-announcement/draft.md`
  - `site/racenavi/README.md`

## Push Back

- 直近投稿と似すぎる話題しか出せていない。
- 機能説明や宣伝文が前に出すぎている。
- RaceNavi か関門ガイドのどちらかに偏りすぎている。
- 具体場面が弱く、ランナーの実感より説明が勝っている。

その場合は、そのまま 10 件を量産せず、分析欄か投稿前のひと言で軌道修正する。
